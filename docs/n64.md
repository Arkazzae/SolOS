# Nintendo 64 emulator (`emu/n64`)

A Nintendo 64 core in Rust with no I/O, built like the NES, Game Boy and GBA cores: the host passes
the cartridge image and the buttons, and gets back the picture, sound, game saves and save states.
It is developed on a PC against public test ROMs and the user's own games.

The goal is full speed on the Zero 2 W. The core has three layers:

- a **reference** (interpreter CPU, low-level RSP, software RDP) that defines correct output;
- **fast paths** that must match the reference bit for bit: an ARM dynarec for the CPU and the RSP,
  NEON for the RSP's vector unit, a multithreaded RDP;
- **high-level emulation (HLE)** of the common graphics and audio microcode, which skips the RSP.

API:

- `N64::new(rom)` builds the console. `run_frame(buttons)` runs one video field (1/60 s). `frame()`
  returns the picture (XRGB8888 with width and height; empty while the video is off). `audio()`
  returns the last field's stereo sound at 48 kHz, left channel first (`SAMPLE_HZ` pairs a second).
  `set_stick(x, y)` moves the analog stick.
- Buttons are bits in the order the pad answers the PIF (`n64::A` … `n64::C_RIGHT`).
- `save_data()` returns the cartridge's save memory (EEPROM, SRAM or FlashRAM) and
  `load_save_data(data)` restores it before the game starts. Save states use the shared `savestate`
  crate.
- The fast paths are switched on with `set_jit` (ARM only; off by default), `set_rsp_acceleration`,
  `set_rdp_acceleration`, `set_gfx_hle` and `set_audio_hle`; `set_rdp_drawers` sets the RDP thread
  count. The game host turns them all on.

## Status

Status (2026-11-05): Super Mario 64, Mario Kart 64, GoldenEye 007, Paper Mario, Ocarina of Time and
Donkey Kong 64 boot, play with sound and keep their saves. On the Zero 2 W six of the eight measured
scenes run at 60 fps or more in `run-n64`; Ocarina of Time (34 fps) and the Super Mario 64 title
scene (46 fps) do not yet. Both 32-bit ARM and 64-bit ARM (AArch64) builds have dynarecs for CPU
and RSP as well as NEON vector unit and RDP rasteriser acceleration.

| Area | State |
|---|---|
| CPU | VR4300 interpreter (the reference) and an ARM dynarec (32-bit and 64-bit); COP0, TLB, FPU with all rounding modes |
| RSP | low-level interpreter (runs any microcode), dynarec, NEON vector unit (32-bit and 64-bit) |
| RDP | software rasteriser on its own threads, accelerated with NEON on 32-bit and 64-bit ARM |
| Graphics and audio | HLE for F3D, F3DEX and F3DEX2 display lists and the ABI1, EAD (Mario Kart 64, Ocarina of Time) and n_aspMain (Paper Mario, Donkey Kong 64) audio microcode; all else runs on the RSP |
| Cartridge | EEPROM 4 and 16 kbit, SRAM 32 KB, FlashRAM 128 KB; CIC 6102, 6103, 6105, 6106 |
| Output | picture from the VI frame buffer, sound from the AI at 48 kHz |

## How it works

### Reference core

- **CPU (NEC VR4300, 93.75 MHz).** An interpreter, one cycle per instruction (the timing of a cache
  hit; cache misses and multiply/divide latency are not modelled). `decode.rs` turns a word into a
  kind and fields; `cpu.rs` executes it. 64-bit registers with sign-extended 32-bit results, delay
  slots (an exception in a slot returns to the branch, with BD set), branch-likely, traps, overflows,
  LL/SC, unaligned LWL/LWR/LDL/LDR and their stores.
- **COP0.** Every register, with write masks. Random counts from the Wired write, Count ticks every
  second cycle, and the Compare interrupt is an event. Registers that do not exist return the last
  value written to COP0. Exceptions set the code, EPC, BadVAddr, Context and XContext; vectors depend
  on BEV and on whether a TLB miss happened inside another exception. ERET.
- **Addresses and TLB.** Kernel, supervisor and user modes; 32-bit addresses (KSEG0 and KSEG1 bypass
  the TLB, kuseg bypasses it under ERL) and 64-bit addresses (xkphys, segments of 2^40 bytes). The
  TLB has 32 entries with page sizes from PageMask, ASID and the G bit, invalid and clean pages;
  TLBR, TLBWI, TLBWR, TLBP. Caches are not emulated (CACHE does nothing).
- **FPU (COP1).** Single and double precision, conversions between them and to integers (W, L),
  ROUND/TRUNC/CEIL/FLOOR, 16 compares, BC1 branches, FCR31 with flags, enables and cause. Rust only
  rounds to nearest, so the other modes are done by hand: the result rounded to nearest, plus the
  side on which the exact value lies (an exact rounding error from fma or a two-sum), gives a
  one-step adjustment and the inexact flag. Cases the VR4300 hands to software (the "unimplemented"
  exception: denormals, quiet NaN inputs, denormal results without FS, conversions of infinities and
  out-of-range values) follow ares and were checked with n64-systemtest. With Status.FR = 0, moves
  and loads see odd registers as the upper halves of even ones, and arithmetic reads fs from the
  even register.
- **Events instead of single steps,** as in the GBA core: the VI every line (interrupt at V_INTR,
  end of field), the COP0 timer, the end of PI, SI and RSP DMA, the end of an audio buffer. The CPU
  runs to the nearest one.
- **Memory.** RDRAM is 8 MB (with the Expansion Pak), big-endian. RCP registers are 32-bit; narrower
  writes hit their lane of the word. RDRAM is four 2 MB modules with their own registers, selected
  by DeviceId; Mode reads with reversed bits, and a module with zero output current does not answer
  (the mupen64plus model), which is how IPL3 calibrates the current and counts memory. MI repeat
  mode is supported.
- **PI.** DMA from the cartridge to RDRAM (and from RDRAM to SRAM and FlashRAM) happens at once; the
  busy flag and the interrupt follow after the time given by the domain timing (LAT, PWD, PGS, RLS).
  Where nothing answers, the bus returns the lower half of the address twice. An IS-Viewer at
  `13FF_0000` collects text from test ROMs and homebrew (`isviewer()`).
- **SI and PIF.** 64 bytes of PIF RAM, DMA both ways, command byte 0x3F (end of boot, ROM lock,
  IPL2 checksum handshake), joybus frames: a pad on each port the host plugs in (one per pad the
  console has, `set_controllers`, each with its buttons and stick), empty other ports, the
  cartridge's EEPROM on channel 5. While rumble is on, each pad has a Rumble Pak: status byte 0x01,
  0x80 read at 0x8000 (where libultra's osMotorInit tells it from a Controller Pak), the motor run by
  a write to 0xC000, the pak's CRC-8 (polynomial 0x85) after each read and write; `motor(port)`
  says what the host's pad feels. The CIC challenge (bit 0x02) sends the 15 bytes from 0x30 to the
  CIC nibble by nibble, high first, and returns its answer. The 6105 computes it with its own carry
  sum (the UltraCIC_C `cic_c.c` routine, checked against mupen64plus on random challenges); the
  other CICs echo the challenge negated.
- **Save memory (`save.rs`, `games.rs`).** A game has one kind or none.
  - EEPROM answers on the joybus: its type (0x0080 for 4 kbit, 0x00C0 for 16 kbit) and 8-byte block
    reads and writes. Writes finish at once.
  - SRAM sits on the PI bus at `0800_0000`, in 32 KB banks selected by address bits 18–19.
  - FlashRAM is driven by commands written to `0801_0000` (n64brew "Flash"): erase a 16 KB sector or
    the whole chip, load a 128-byte page and program it (programming only clears bits), and the array,
    status and ID read modes. Erase and program finish at once. It imitates the MX29L1100, which
    every libultra version handles.
  - Nothing on the cartridge says which memory a game has, so `games.rs` holds the N64FlashcartMenu
    list (`src/menu/rom_info.c` at commit `7fcef17d92ee` of
    github.com/Polprzewodnikowy/N64FlashcartMenu): the game code from the header (0x3B–0x3E; three
    letters match every region), sometimes the version (0x3F), a few cartridges by checksum
    (0x10–0x17), and homebrew with code "ED", which states its kind in the version byte. A game not
    on the list has no save memory.
  - `save_data()` returns the bytes as they lie in the chip, like a flash cart's `.sav` file, and
    `load_save_data()` takes the same. Empty FlashRAM is all FF, the others all zero.
- **RSP.** DMEM and IMEM, registers, DMA with row stride (instant), the semaphore, and the processor.
  The scalar unit is a 32-bit MIPS without multiply, 64-bit instructions, branch-likely or
  exceptions; BREAK halts it and interrupts the CPU. The vector unit is COP2 (`vu.rs`): 32 registers
  of eight 16-bit lanes, a 48-bit accumulator in three slices, flags VCO, VCC and VCE, saturating
  multiplies, compares and clipping (VCH, VCL, VCR), reciprocal and reciprocal square root from
  tables (as in ares, verified on hardware), and every vector load and store, including the
  transposing ones. COP0 of the RSP is the SP and RDP registers.
  - The RSP runs at 2/3 of the CPU clock, in slices of 256 of its cycles, as an event while it is not
    halted. An instruction takes a cycle, plus what the pipeline adds and saves (n64brew "RSP
    pipeline"): one empty cycle after a branch's delay slot, a register loaded or read through
    MFC0/MFC2/CFC2 is ready after three cycles (an instruction that reads it sooner waits), and a
    vector instruction beside a scalar one issues in the same cycle. Vector register delays and the
    conflicts that stop a pair are ignored.
  - IPL3 6105 depends on this: the RSP waits in a loop for the CPU's semaphore and gives up after
    2 million iterations. At seven cycles an iteration, as on hardware, it waits long enough; at one
    cycle an instruction it gave up before the CPU had loaded the game.
- **RDP interface (`rdp.rs`).** DPC_START waits for DPC_END, which starts fetching commands from
  DPC_CURRENT, from RDRAM or from DMEM (the XBUS bit in DPC_STATUS), at once and command by command;
  a command cut off by the end of the list waits for the rest. FREEZE halts the fetch and SYNC_FULL
  raises the DP interrupt. State: the modes (Set Other Modes), combiner, colours, scissor, colour,
  depth and texture images, eight tiles, and 4 KB of TMEM filled by Load Block, Load Tile and Load
  TLUT.
- **RDP drawing (`raster.rs`).** A software rasteriser of what games use, modelled on angrylion
  where the chip's arithmetic matters.
  - Triangles: a major and two minor edges in s15.16 on line quarters. A pixel is drawn when its
    centre lies between the edges on any of its four quarters (half-open, so triangles sharing an
    edge leave no gap and do not overlap). Shade, s, t, w and depth come from coefficients along the
    major edge and across the line. Copy mode steps the texture coordinate a quarter per pixel.
    A pixel whose alpha reduces the coverage to zero (cvg_x_alpha, cut-out textures) is not written.
  - Textures: perspective divide with the RDP's reciprocal table, shift, tile-origin subtraction,
    clamp, mask and mirror; RGBA16/32, IA4/8/16, I4/8 and CI4/8 with RGBA16 or IA16 palettes;
    bilinear filtering from three neighbours as the RDP does, or point sampling. Without mipmaps the
    LOD fraction is at its maximum (255).
  - Combiner (A − B) × C + D in both cycles with 9-bit clamping; alpha compare; depth test in the
    compressed 16-bit Z format (angrylion's tables; opaque, interpenetrating, transparent and decal
    modes); blender (P × A + M × B, the chip's formula for force_blend; in 2-cycle mode the first
    cycle always blends, e.g. for fog).
  - Rectangles: fill mode writes the fill colour, copy mode the texels directly (alpha as alpha
    compare), 1/2-cycle mode goes through the whole pipeline. Fill and copy include the last pixel of
    each edge.
  - Left out on purpose: antialiasing (every pixel is fully covered; the blender only mixes with
    force_blend), dithering (beyond the noise alpha compare uses), LOD and mipmaps, chroma key, YUV,
    the hidden RDRAM bits.
- **Picture.** At the end of each field the VI takes from the RDRAM frame buffer (origin from
  VI_ORIGIN, row stride from VI_WIDTH, 16-bit RGBA5551 or 32-bit RGBA8888) the pixels it shows: the
  active area H_VIDEO and V_VIDEO (in half-lines) times X_SCALE and Y_SCALE. There is no scaling to
  the TV and no VI filters (antialiasing, dither filter, gamma). `frame()` returns nothing while the
  video is off (type 0 or empty H_VIDEO).
- **AI.** Two buffers queued, an interrupt when a buffer starts playing, timing from AI_DACRATE
  (VI clock / (DACRATE + 1)). The playing buffer (16-bit big-endian stereo) is resampled to 48 kHz
  (nearest sample) from RDRAM as the converter would read it.
- **Save state.** 8.5 MB, almost all RDRAM. The state carries the ROM's hash, so a state of another
  game or a damaged one is rejected without changing the machine; after loading, the machine
  continues instruction for instruction as before. Acceleration preferences and counters are host
  data and are not saved; the format is version 3 throughout.
- **Boot.** The state after IPL1 and IPL2 (Nintendo's PIF code) is set directly.
  - Config `0006_E463` (n64brew "Initial Program Load"). IPL1 sets Status to `3400_0000`, but a game
    finds `2410_00E0` (IPL3 does not change it). The rest of COP0 has the values the krom and Lemmy tests
    read on hardware: Cause `B000_007C`, EPC, ErrorEPC and BadVAddr all ones, Context `007F_FFF0`.
    The TLB is as after libultra's `osUnmapTLBAll` (entries in unmapped kseg0; all zeros would hit
    address 0).
  - RSP halted, VI_V_INTR = 3FF, PI domain 1 timing from the first header word, IPL3 (ROM
    0x40–0xFFF) in DMEM from 0x40, registers s3–s7, t3, sp and ra as in mupen64plus's IPL2
    (`bootrom_hle.c`), the CIC seed in s6 from the n64brew "PIF-NUS" table, and the start at
    `A400_0040`. The CIC is recognised by the sum of the boot code's words (mupen64plus's table).
  - The game's IPL3 does the rest: it initialises RDRAM, loads 1 MB of the game by PI DMA, checks its
    checksum (a bad one would halt the console) and jumps to it. IPL3 6103 and 6106 load the game 1
    and 2 MB lower than the header says (Paper Mario: header `8012_5C00`, code from `8002_5C00`;
    `entry()` returns the real address). IPL3 6105 decrypts RSP code in IMEM from the IPL2 words left
    there (as mupen64plus does) and starts the RSP, which after the CPU's semaphore copies part of
    IPL3 to RDRAM at `2F_B1F0`, 24 rows every 0xFF0; Donkey Kong 64 waits for a word from that copy.
  - Milestone: Super Mario 64 runs its own IPL3 (24.3 million instructions) to the entry point
    `0x80246000`, with the first megabyte of the game in RDRAM and osMemSize = 8 MB.

### CPU dynarec (`src/jit`)

Available on 32-bit and 64-bit ARM. It is switched on with `set_jit(true)` or `run-n64 --jit`; the
interpreter stays the default and the reference.

- **Blocks.** Up to 64 guest instructions are translated to A32 or A64. In 32-bit ARM, a 64-bit guest
  register is a pair of ARM registers; 32-bit results keep their sign extension. In 64-bit ARM (A64),
  a guest register fits a 64-bit host register, and 64-bit operations (including DMULT, DMULTU, DDIV,
  DDIVU) run natively. A block never crosses a page or an event boundary, and a RAM store always ends it.
- **Native instructions.** Shifts, logic, add and subtract (including trapping ADD, SUB, ADDI, DADD,
  DSUB, DADDI; an overflow exits before the instruction for the interpreter's exception), compares, HI/LO,
  MULT/DIV, RDRAM loads
  and stores (LB…LD, SB…SD), all integer jumps and branches and BC1F/BC1T/BC1FL/BC1TL; in the FPU:
  loads, stores and moves (LWC1, SWC1, LDC1, SDC1, MFC1, DMFC1, MTC1, DMTC1, MOV), ADD/SUB/MUL/DIV,
  SQRT and NEG/ABS in both precisions, C.cond, ROUND/TRUNC/CEIL/FLOOR/CVT.W in both precisions,
  CVT.S.W/D.W/D.S/S.D, CFC1, CTC1 and
  CACHE. The FPU arithmetic runs on the host FPU only when the VR4300 would round the same way: round to
  nearest (or toward zero for CVT.W.S), normal or zero operands, a normal or exact-zero result, no
  divide by zero. The inexact flag is computed exactly (two-sum for sums, an exact remainder or
  fused multiply-subtract for products and quotients). Other cases leave the block before the
  instruction and the interpreter does it. The enable bits matter: libultra sets
  `FCR31 = FS | EV`, so a fast path that required all enables clear never ran.
- **Instructions the compiler does not know** (COP0 reads but Status, and PRId, CacheErr and
  TagHi; L conversions on A32) run inside the block through a call to
  the interpreter (`interpret` in `jit/mod.rs`).
  The block saves its cycles and PC first and goes on only if nothing changed the flow: no device
  access, no write to the block's own source, no event due, no pending interrupt. ERET, SYSCALL,
  BREAK, MTC0 (but Status's) and TLB operations end the block before themselves.
- **Status.** MFC0 and MTC0 of Status are native: libultra's `__osDisableInt` and `__osRestoreInt`
  (Star Wars Episode I: Racer calls each about 3300 times a field) no longer stop a block. MTC0
  writes Status and the COP0 latch where it changes only IE and the interrupt mask (otherwise the
  block exits before it and the interpreter does it: a change of mode, mapping or CU1 stops a
  block), and an interrupt it lets through ends the block after it, for the dispatcher to take. A
  block checks once that COP0 is usable (kernel mode or CU0).
- **Registers held.** Within a block the low words of guest registers live in five ARM registers
  (r6–r10, saved by the callee, so routine and interpreter calls keep them); the least recently used
  is let go when another is needed. A register is read from `Cpu` once; a 32-bit result goes only into
  its ARM register (its sign extension is the value) and is stored where the block leaves: at each
  exit through a stub (with two or more changed registers through a shared exit routine given a word
  that describes them), before an interpreted instruction (after which nothing is held, as it may
  write any register), at the block's branch and at its end. A 64-bit result is stored at once and the
  ARM register lets go of the guest's. Whether a held register is a sign-extended word is known at
  compile time (after a 32-bit result, or once checked): then AND/OR/XOR/NOR, SLT(I)(U), SRA(V),
  ORI/XORI and the branches' comparisons use the low word alone. r6 leaves the pool at the branch to
  hold its condition. Where a likely branch's slot runs on one way only, both ways meet with
  everything stored and nothing held.
- **Memory guards.** The block adds the offset to a base that is a sign-extended word (checked once a
  block; the exception, a base just below KSEG0 that a positive offset carries into it, exits and the
  interpreter does that access), setting the flags, and calls one of eight shared guard routines
  (loads and stores by size): overflow, KSEG0/KSEG1, alignment and the RDRAM size (one compare of the
  rotated address), then the RDP piece mark (marks and draws known finished with one LDRD); a store's
  guard also returns whether its page holds code. About four words in the block for each access. On
  failure the block returns the number of instructions it completed and the interpreter performs the
  access (a device, or an exception at the right place). FPU arithmetic is in eight more routines.
- **Direct branches.** Blocks reach the routines (link, guards, FPU, exit) with direct B/BL, bound
  when the block is placed in code memory (`CodeMemory::place`; the routines come first in an emptied
  memory, so every branch is in reach); the context no longer carries their addresses. Calls through
  registers missed the Cortex-A53's branch target buffer across thousands of call sites: in Super
  Mario 64's title mispredicted branches fell from 0.12–0.15 to 0.07 million a field.
- **Code size and compile time.** Inline guards (about 14 words each) made the title's blocks 84
  bytes a guest instruction and gained only 2% (the hot set, 1.3 MB, is far beyond the L1I and L2);
  with shared guards hot code is about 38 bytes a guest instruction and stubs 12. Compiling is
  frequent (Mario Kart 64's race compiles about 70 blocks a field from its state), so the compiler
  does not allocate per exit and placing a block patches it in code memory without a copy.
- **Delay slots.** A jump ends the block. A slot that is plain arithmetic, an RDRAM load or store,
  or a native FPU instruction is compiled into the block (a likely branch that is not taken skips it
  and does not count its cycle); anything else is done by the interpreter. A branch to itself is left
  as it is so that idle-loop skipping can see it. A jump in the last word of a KSEG0/KSEG1 page
  takes its slot from the next page, and the block covers both.
- **Control state.** Cpu's control state (pc, next_pc, current_pc, delay_slot, current_delay) comes
  first in the struct, so a block writes it once, after its jump's slot, with an STM, an STRD and an
  STRH; until then the PC in Cpu stays the entry PC that every target and link is computed from. The
  slot's exits write the state the jump leaves (a routine of the block's, `before_slot`), and a store
  into code in the slot the state after it (`after_slot`).
- **Code changes.** A block's source words are compared on entry (`same_words`), but only when the
  code generation has changed. Writes (bus writes, the three RDRAM DMAs, RDP drawing, native stores
  into a code page) bump the generation if they hit a page with compiled code, and only if they hit a
  256-byte chunk the JIT compiled from. Reads never bump it. Machine writes call `wrote_rdram`,
  reads `touch_rdram`. `--verify-jit` compares the source on every entry and stops when code
  changed without a write.
- **Linking.** A block that ends in a jump with its slot goes straight to the next block through a
  shared link routine, without returning to the dispatcher. It passes the PC it went to in r0 and r1,
  its result in r2 and in r12 the links to try: one for J and JAL and for each way of a conditional
  branch (the block picks it by its condition, so the routine compares one PC), four for JR and JALR
  (returns; a second routine compares them in turn). A link holds the target's PC (its low word), the
  generation it was made at, the target's code address and instruction count. The routine takes it
  if the target is in the same page or in KSEG0/KSEG1 and finishes before the next event: a word of
  the context holds the cycles left to it, which each link is charged (the dispatcher, and
  `interpret` before an interpreted instruction, count the machine's cycles from it,
  `N64::cycles_left`). Otherwise it returns to the dispatcher, which fills the link (only in the set
  the last block missed: a stale one could push out a good link). Outside kernel mode no link is
  taken. Flushing the code memory (32 MB) clears all links. Between blocks the dispatcher
  (`run_jit_blocks`) also goes on to the next block at once while the next PC is plain and in the
  same page.
- **Mapped code.** Code in mapped space (GoldenEye runs at `0x7000_0000`) is translated through the
  TLB. `tlb_lookup` has a 64-page direct-mapped memory (4 KB pages, keyed by virtual page and ASID)
  in front of the 32-entry search; TLBWI, TLBWR and loading a state clear it. The dispatcher also
  remembers the page it last entered from (virtual page with ASID, mode and TLB epoch).
- **Idle loops.** A jump to itself with a NOP in the slot skips its remaining iterations to the
  nearest event, keeping cycles, slot parity and EPC/BD on an interrupt. Only for code in readable
  RDRAM at a direct kernel address, without a link-register write or device reads. This works in the
  interpreter and after natively executed jumps. `step()` still runs a single instruction.
- **RDP overlap.** The RDP draws on other threads while the CPU runs, so each native RDRAM access
  also reads the mark of its 1 KB piece (in the guard routine) and leaves the block (the interpreter
  then waits for the drawing) if a draw that may touch it is not finished.
- Code memory belongs to the machine and is freed with it. A clone or a loaded state starts with an
  empty cache.

### RSP dynarec and NEON (`jit/rsp_compile.rs`, `vu/neon.rs`)

- **Dynarec.** Translates RSP microcode from IMEM to A32: a block runs from an address to a jump and
  its slot, to MTC0 or BREAK (after which the RSP may stop or have new code), or for 64
  instructions. Scalar arithmetic, branches and DMEM accesses are native. Native too: the MFC0 reads
  of the SP and RDP registers (not the semaphore, whose read takes it), the DMA address
  writes and semaphore release by MTC0, MFC2/MTC2 of a whole lane, LSV/LLV/LDV and their stores at an
  even element, and whole aligned LQV/SQV; a wrap past the end of DMEM stays in the interpreter. Vector
  computations call a per-function entry (`vu::entry`) chosen at compile time. The interpreter stays
  the reference.
- **Timing.** The time is the interpreter's (`rsp::pipe`), computed at compile time for the pipeline
  state the block is entered with (a code variant for pairs, a vector instruction and a slot). The
  clock is a base in two registers plus a constant; only where a register read may still be loading
  from an instruction whose time the compiler does not know does the code compare with `ready` and
  shift the base. Before each instruction the block leaves when the RSP's slice has ended.
- **IMEM changes.** Microcode, overlays and a few words written like data change IMEM several times
  a field. A block remembers its words, and up to four versions are kept per address and variant. An
  IMEM write (DMA or CPU) bumps a counter and stamps its 256-byte pages; a block that matched at a
  given counter stays valid until one of its pages is stamped later, and only then are its words
  compared. About three compilations a field remain in the before-the-castle scene.
- **Chaining.** A block that falls through or ends after a jump slot (JR too) enters the next one
  directly. A table has, for each IMEM address and entry variant, a place behind the block's
  prologue and the write counter at which the dispatcher last found it valid. The code checks the end
  of the slice, the counter and that code exists, shifts the clock base and jumps. It does not chain
  after MTC0 or BREAK, in a slot either.
- **NEON vector unit.** Each frequent operation is one asm block: it loads vs and vt, broadcasts the
  element through `vtbl` with a byte-index table for each of the 16 element fields, and stores the
  result and the accumulator slices straight into `Vu`, after all reads (so vd may equal vs or vt).
  VCO and VCC bits are built with `vtst` and three `vpadd`. Operations: VMULF/VMULU, VMADH/VMUDH,
  VMADM/VMADN, VMUDL/VMUDM/VMUDN, VADD, VSUB, VADDC, VSUBC, VLT, VEQ, VNE, VGE, VMRG, the logic
  group, VMACF, VMADL, VSAR, VNOP, and the broadcast in VRCP/VRSQ/VMOV. The kernels use no saturating
  instructions, so the sticky FPSCR.QC bit stays untouched, and only registers q0–q3 and q8–q15,
  which the ABI lets them clobber. The scalar unit stays the reference for VMULQ, VMACU, rounding,
  VABS and VCH/VCL/VCR. NEON is detected once per process with `getauxval(AT_HWCAP)`.
- **Memory transfers.** LQV/SQV at element 0 with a 16-byte-aligned address copy a whole vector
  through fixed-size arrays; LDV/SDV at element 0 or 8 copy the half, unless the eight bytes wrap at
  the end of DMEM. This is plain Rust and also runs without NEON. Everything else uses the byte loops.

### RDP threads and fast spans (`rdp_thread.rs`, `raster.rs`)

- **Threads.** The machine thread keeps the DPC interface, all RDP state (this goes into the save
  state), TMEM loads and the SYNC_FULL interrupt. It sends the drawing threads, in batches, the
  state-setting commands (the same `Rdp::set_state` on both sides), the changed TMEM bytes and the
  draws with the CPU cycle count (alpha noise). A batch goes after 32 draws, or earlier when
  something waits or at the end of a field and on a state save. `Raster` is a set of methods on the
  RDP state, RDRAM and cycles, so the same code draws on either side; a drawing thread touches only
  the colour and depth images.
- **Line interleave.** There are `N` drawing threads (all cores but the machine's, at most three: three
  on the Zero 2 W, so the emulator uses all four cores; `--rdp-threads N`, `set_rdp_drawers`). Each
  receives every batch and keeps its own copy of the RDP state, but draws only the lines with
  `y mod N` equal to its index. Every pixel of the image has one thread that draws it in RDP order,
  and consecutive lines cost about the same. Triangle edges are recomputed for each line, so skipping
  a line moves nothing. When the colour or depth image changes (another address or width), the same
  bytes may belong to another thread's lines, so all threads meet at a barrier. They also meet around
  the VI image, which the first thread takes. The alpha-noise seed depends on cycles and x, not y, so
  the result is the same for any thread count.
- **Page marks.** Each draw marks the 1 KB pieces of RDRAM it can reach: the rows from YH to YL of a
  triangle, or ULY to LRY of a rectangle (with the last row that fill and copy draw), clipped to the
  scissor, in the colour image and, for 1/2-cycle draws that compare or write depth, the depth image.
  Draws and VI images have sequence numbers; a piece holds the number of the last draw that can reach
  it, and each drawing thread reports the last number it has finished. Pieces, not 4 KB pages: Paper
  Mario keeps its depth buffer at 0x400, in the page of the exception vectors, and with page marks
  the CPU waited for the depth clear (about 17 ms) at every interrupt. Before the machine thread
  touches RDRAM (`touch_rdram`: CPU bus reads and writes, RSP, PI and SI DMA, the AI buffer, the VI
  image, RDP command fetch and texture loads) it waits only if the draw that marked that piece is
  unfinished, and only until that draw. The wake-up cannot be lost: the machine writes which number
  it waits for before it looks at progress, and the thread writes progress before it looks for a
  waiter (both SeqCst). A state save, a machine clone and `peek` wait for everything. Numbering
  restarts at every `sync`, which is forced before 2^31.
- **Pictures.** The drawing threads convert each VI picture, each its own lines between the same two
  barriers, one slice per line from RDRAM. At the end of `run_frame` the machine takes the newest
  finished picture without waiting, so it can be a field or two behind, unless exact pictures are
  requested (`set_rdp_exact_pictures`, `--exact-pictures`, used by comparisons).
- **Texture loads.** Load Block and Load Tile copy whole words (on odd lines with the halves
  swapped) when the texture is not 32-bit, the source is inside RDRAM and the target inside TMEM
  without wrapping; otherwise the byte path is used. Every load reports the TMEM bytes it changed,
  and the batch carries only those. LOAD_TILE and LOAD_TLUT also set the tile size they use (like
  SET_TILE_SIZE), so the drawing threads get a SET_TILE_SIZE after such a load.
- **Span paths.** A span is one scanline of a draw. `pixel()` is the general path. Faster spans are
  chosen per span:
  - `span_sampled`: 1-cycle with a perspective-textured, bilinear, combiner-plan pixel; modes, tile,
    colours, blender selectors and alpha thresholds are worked out once a span.
  - `span_opaque`: the same without the alpha channel when the 16-bit pixel takes only RGB and a
    coverage bit: RGBA16 (also IA8 and IA16), blender that only writes (or force_blend returning the
    combiner colour, or plain alpha blending with memory), no alpha compare and no cvg×alpha, Z from
    attributes. Also spans without a texture. Each of the four Z-mode pairs has its own loop. Tile
    axes are worked out once a span and TMEM and RDRAM are fixed-size arrays (no bounds checks).
  - `span_cycles`: every other one- and two-cycle span (two-cycle modes, palettes, point sampling,
    any combiner and blender): `pixel()`'s steps with what the modes fix worked out once a span. Each
    combiner cycle is its plan or its inputs picked once as whole colours or alphas; the blender's
    selectors, both tiles' axes and texel formats (palettes included) are fixed for the span; only
    the texels the combiner's cycles take are sampled (sampling has no other effect, and the
    profiling counters count what `pixel()` would), each through a sampler with its tile's texel
    format and filter fixed; a blender cycle that gives the pixel back skips its arithmetic. Paper Mario and Ocarina of Time drew nearly all
    their pixels through `pixel()` before (Ocarina of Time draws in two-cycle mode, Paper Mario with
    palettes and point sampling).
  - `span_copy`: copy mode, `copy_pixel()`'s steps with the tile's axes worked out once (a fifth of
    Paper Mario's pixels).
  - The filter reads the three texels of the triangle it needs, not all four corners. RGBA16 is
    recognised once a sample and uses a dedicated RGBA5551 decoder.
  - The combiner plan is worked out at Set Combine Mode (command 3C), not per pixel, and holds only
    the formula kind and source numbers. Classes: D only, texel 0/1 × shade, texel 0/1 × primitive
    (also with A/C swapped), a lerp between primitive and shade by texel 0/1. Other modes use
    `combine_selected`, which picks each argument once as a whole colour and computes
    (A − B) · C + D without branches in the channels; `combine_reference` stays for comparison.
  - Whether the blender needs the memory pixel is decided once a span (P=memory always; M=memory or
    B=memory-alpha only in a cycle that actually blends; the first 2-cycle cycle always blends, the
    last only with force_blend), and the read is skipped when it is not needed.
  - The plans are rebuilt after Set Combine Mode and after a state load; they are not saved.
- **NEON (`raster_neon.rs`).** On both the 32-bit and 64-bit ARM builds (NEON found by HWCAP on 32-bit,
  always present on AArch64) `span_opaque` and `span_cycles` draw a pixel's colour channels as the four
  16-bit lanes of a D register (in `uint16x4_t` on AArch64): small asm blocks or AArch64 NEON intrinsics
  on values kept in vector registers. Texels are decoded to four packed bytes (RGBA5551 by two 256-entry
  tables whose parts add without a carry, IA8 and IA4 by tables, the rest by integer arithmetic) and
  widened. The three-texel filter is `(corner · (32 − fs − ft) + along_s · fs + along_t · ft + 16) >> 5`
  per lane, the scalar formula with 32 · corner moved inside the shift (checked for every input). The
  shade's attributes step in lanes with 128 added to their integer parts, so clamp9 is `clamp((v &
  0x1ff) − 128, 0, 255)` (VSHRN, mask, sub 128, max 0, min 255). `span_opaque`'s plans multiply in 16
  bits (their inputs are 0–255, so clamp9 changes nothing); `span_cycles`' combiner picks each cycle's
  A, B, C and D lanes with VTBL (`vtbl4_u8` on AArch64) from [combined, texel 0, texel 1, shade] or-ed
  with fixed lanes, works (A − B) · C in 32 bits and clamps as above; a cycle whose every lane is a
  product plus a sum within 0–255 branches to 16 bits without clamp9. The blender mixes on lanes; the
  RGBA5551 store sums the shifted fields across lanes (`vaddv_u16` on AArch64). The scalar spans stay
  for the other targets, and `pixel()` is the reference.
- **Texel loads.** The in-order A53 waits at each load's use, and the compiler kept a texel's loads
  after one another; an empty asm block that takes the three (or six) loaded values makes them issue
  together. 16-bit texels and palette entries are loaded as halfwords where the tile's TMEM address
  and line are even (always, from commands; otherwise bytes).
- **span_cycles with NEON** takes the one-cycle spans `span_opaque` leaves (`span_sampled` and
  `span_one_cycle` stay for the scalar build). The combiner lanes, whether the second cycle gives the
  first's colour back (then it is left out) and which texels are used are kept per thread and made
  again only when the combine mode, the colours and constants it picks (primitive, environment, key,
  primitive LOD fraction, the two convert constants) or the noise's bits change. Two tiles of one
  format with the same axes are sampled together (coordinates, wrap and weights once; Ocarina of
  Time's backgrounds). `span_opaque` does not fetch a texel its plan does not take (Mario Kart 64's
  shade-only spans with a texture).
- **Depth.** The test compares compressed depths: z_compress gives the largest code whose depth is at
  most z and z_decompress grows with the code, so z < z_decompress(code) exactly when z_compress(z) <
  code (checked for every input; decals still decompress). z_compress finds its shift by arithmetic,
  not a table.
- **Fill rows** that do not wrap RDRAM are the fill colour's bytes repeated from the first pixel's
  byte, written four at a time.
- **Triangle setup.** The edges' sums are worked in i32 when every slope times the quarter lines is
  below 2^29 (the same results); a span's first attributes come from one NEON block (VMLA for the
  major edge, VMULL.S32 and VSHRN for the offset's 64-bit products) when the offset fits 32 bits. Both
  only with acceleration on, so `--verify-rdp`'s reference still uses the i64 code.

### Graphics HLE (`gfx_hle.rs`)

Instead of running a graphics microcode on the RSP, the HLE reads the display list itself and builds
RDP commands from it at once, which the RDP threads draw as before. A task is recognised by the
version string in the microcode's data (OSTask in DMEM at `0xFC0`):

| Microcode | Games |
|---|---|
| F3D "RSP SW Version: 2.0D" | Super Mario 64 |
| Rare's F3D variant "2.0G" | GoldenEye 007 |
| Rare's F3D changed again (no version text: known by its data's first 0x200 bytes) | Perfect Dark |
| F3DEX 0.95 and 1.x (GBI1), also .NoN | Mario Kart 64 |
| F3DEX2 and F3DZEX (GBI2), also .NoN ("fifo 2." or "xbus 2.") | Ocarina of Time (F3DZEX.NoN 2.06H), Donkey Kong 64 (F3DEX 2.07), Paper Mario (F3DEX 2.08) |
| F3DEX.Rej (GBI2, "fifo 2.06") | Resident Evil 2 |
| S2DEX 2.05–2.08 (GBI2), "RSP Gfx ucode S2DEX fifo/xbus 2.0x" and "RSP Gfx[Safe] S2DEX fifo 2.05" (`s2dex.rs`, below) | Majora's Mask, Resident Evil 2; also in Ocarina of Time's and Mario Party's ROMs |

Other microcode (audio, unknown graphics) runs on the RSP as before. A task ends at once: the RSP
halts with task-done and the interrupt, as after a microcode BREAK, after a time close to its work.

- **Arithmetic** is floating point, following the commands' definitions in `gbi.h`: s15.16
  matrices, viewport, lights, texgen (in s10.5, S from LookAtX), fog, clipping in clip space (the
  near plane first, then the sides at the clip ratio), culling by winding, triangle fans in the
  microcode's order, and triangle setup as in libdragon's rdpq (edges, colour, texture, Z). The screen
  is in pixel quarters, as in the microcode, and triangles with zero area on those quarters are not
  sent. A triangle is dropped when all three vertices lie beyond the same screen edge (±w) or the near
  or far plane, not only beyond the clip planes.
- **Variants.**
  - Rare's microcode has a four-triangle command (0xB1: four bits a vertex, drawn from the second,
    as the edges show) and reads vertex texture coordinates swapped (S from t, T from s), with the
    scale from G_TEXTURE in steps of 1/2048 instead of 1/65536.
  - Perfect Dark's microcode loads 12-byte vertices (x, y, z, flags, colour offset, s, t), 4 bytes
    on from the DMA-aligned address when the address has bit 2. Their colour, or normal when lit, is
    4 bytes at that offset in a table that command 0x07 copies into DMEM (words from the offset in
    w0's second byte down to 0, as the DMA brought them; a smaller table leaves the rest). It has
    GoldenEye's four-triangle command, takes s and t as F3D does, and always shades smoothly.
    G_POPMTX and G_CULLDL do nothing. It has room for two lights, with its G_MOVEMEM table at 0x230.
    It does not clip at the near plane: what lies nearer is drawn at depth 0. It rejects a triangle
    whose three vertices lie beyond the same screen edge or the far plane, and clips against w = 0,
    the far plane, then y and x high and low at the clip ratio, by the vertices' codes. Each cut list
    starts where the polygon comes back in, and the fan is drawn first triangle first.
  - F3DEX 1.x differs from F3D in G_VTX (start × 2, count in bits 10–15), indices × 2 in G_TRI1 and
    G_CULLDL, G_TRI2 (0xB1), G_MODIFYVTX instead of G_RDPHALF_CONT (0xB2), the texture-rectangle
    halves in G_RDPHALF_1/2, G_BRANCH_Z (0xB0), and Mario Kart 64's G_LINE3D (0xB5) with four
    indices.
  - F3DEX2 has its own opcodes (G_VTX 0x01 with the buffer end instead of start, G_TRI1/TRI2/QUAD
    0x05–0x07, G_MTX 0xDA with the push bit inverted, G_MOVEWORD/G_MOVEMEM 0xDB/0xDC with lights every
    24 bytes, G_GEOMETRYMODE 0xD9 with a clear mask, RDP halves 0xE1/0xF1, G_MODIFYVTX, G_BRANCH_Z,
    G_CULLDL), 32 vertices instead of 16, and indices × 2; G_TRI2 draws the second triangle first. The
    .NoN variant does not clip at the near plane (it clips only what is behind the eye and sets depth
    nearer than the plane to the plane). Light directions are taken as they are (in 128ths), not
    normalised.
  - F3DEX.Rej is F3DEX2 that leaves out a triangle partly outside the clipping box instead of
    clipping it, and draws G_TRI2's (and G_QUAD's) first triangle first.
- **Default lights.** A game that lights without setting lights gets the microcode's own defaults. In
  F3D and F3DEX 1.x the G_MOVEMEM address table is in the data at `0x2F0` (viewport, two lookat
  lights, then lights) and the default ambient is red; the HLE reads it at the start of every task.
- **Frozen RDP.** Donkey Kong 64 freezes the RDP (DPC_STATUS) for the task and thaws it at the next
  VI, so the DP interrupt comes a field later and throttles the game. The HLE's commands therefore
  wait while the RDP is frozen and go ahead of what the RDP takes from its FIFO after the thaw. A
  machine clone (save state) does not take them: a state saved while the RDP is frozen loses one
  frame of picture.
- **Another microcode.** A display list may load another microcode (G_LOAD_UCODE: its text at w1,
  its data at G_RDPHALF_1's address). F3DEX2 and S2DEX keep DMEM below 0x180 (matrices, viewport, the
  scissor at 0xC0, other modes at 0xC8, the saved G_RDPHALF_0 and _1 at 0xD0 and 0xD8, segments at
  0xF8, the list's stack at 0x138) and load the new data from 0x180 on; the new code goes on with the
  next command. The HLE follows: S2DEX where F3DZEX loads it (Majora's Mask's intro, title and menus,
  Ocarina of Time's pre-rendered rooms), F3DEX2 where S2DEX loads it (Resident Evil 2 draws its
  background with S2DEX, then its 3D with F3DEX.Rej, in one task). F3DEX2 loaded again starts what it
  keeps above 0x180 (geometry mode, lights, fog, G_TEXTURE, clip ratio, the forced-matrix flag) as its
  data has it. Before a task the HLE follows its lists (calls, branches, ends, segments, G_BRANCH_Z
  both ways, G_CULLDL as not culled, S2DEX's G_SELECT_DL as a call, on through the loads it knows),
  each list once a segment table: a task that can load a microcode it does not know, or any from
  F3DEX 1.x, runs on the RSP whole (`run-n64 --hle` counts them). The scan reads about as many
  commands as the task has (2,500–5,600 in Majora's Mask and Ocarina of Time). Before the HLE
  followed loads, it stopped at G_LOAD_UCODE without the list's SYNC_FULL, and Majora's Mask waited
  3 seconds a frame (its "RCP is HUNG UP" timeout).
- **The DP interrupt** of a SYNC_FULL the RSP sends (or the HLE, running a task) comes when the RSP
  stops (BREAK, or the CPU halting it), after the SP interrupt: the RDP finishes what the microcode
  sent it after the microcode itself. Our RDP draws a command as soon as DPC_END reaches it, so the
  interrupt used to come while the microcode still ran (with the HLE, at the task's start).
  Resident Evil 2's scheduler takes a DP interrupt before the task's SP one as a task done twice, and
  its frame state then stops the main loop after the N64 logo. Commands the CPU sends interrupt at
  once.
- **Forced matrix.** gSPForceMatrix puts the combined matrix where F3DEX2 keeps it (G_MOVEMEM
  G_MV_MATRIX, DMEM 0x80) and G_MW_FORCEMTX sets the byte at 0x1D9 that says it is up to date (G_MTX
  and G_POPMTX clear it); then it is used as it is. Episode I: Racer loads every object's matrix this
  way: without it none of its 3D was drawn.
- **Fixed point for Perfect Dark.** Its vertices follow the microcode's fixed point: the modelview,
  projection and their product kept in s15.16 and multiplied as the microcode does (each product
  floored, the sum saturated), the transform exact, then w scaled by the perspective normalisation
  (12–13 in 65536ths, leaving a near w about ten bits) before the RSP's reciprocal table and one
  Newton-Raphson step, and the integer viewport. In floating point, 2D drawn with large coordinates
  against small scales landed a quarter pixel off, and 3D slivers came and went. `--compare-hle`:
  3528 of 3528 triangles close on its agent menu, and over 1900 fields from power-on 348,738 of
  348,743 with one task holding an extra sliver (the cut vertices are still worked out in floating
  point).
- **Task time** is computed from the work done and fitted to the microcode's RSP cycles on scenes of
  five games, to within 8% (Paper Mario 15%). A fixed time shifted the pace of games (DK64).

  | Microcode | Per command | Per vertex | Per triangle | Per triangle sent to the RDP |
  |---|---:|---:|---:|---:|
  | F3D | 54 | 61 | | 740 |
  | F3DEX2 | 32 | 64 | 32 | 121 |
  | F3DEX 1.x | 43 | 86 | 43 | 333 |
  | Perfect Dark's | 82 | 74 | 157 | 321 |

  Perfect Dark's is fitted over six scenes, each within 2%, leaving out the time the microcode waits
  for the RDP the game keeps frozen.

- **Comparison.** `--compare-hle` runs the HLE on a copy of the machine before each graphics task,
  collects its RDP commands, then lets the RSP run the microcode and compares the two streams:
  commands other than triangles word for word, triangles by vertices (within 1 pixel in x and a
  quarter in y, in any order, since the microcode picks the "middle" vertex on a y tie). It collects
  commands up to the next graphics task (some games give the RDP its commands only after the task
  ends), skips RDP NOPs, and compares syncs by kind only. Over 20 fields of eight scenes every
  non-triangle command is identical; triangles are close in 90% before the castle, over 99% on the
  SM64 title, GoldenEye after 600 fields and DK64, 95% in Ocarina of Time, 68% at the GoldenEye barrel
  and 77% in Paper Mario. The rest is a different split of a polygon clipped at the guard band's edge.
  The gate is the picture: pixels that differ by more than 10%. They are at most 0.14% (0.06% for
  F3DEX 1.x), except DK64 (2%: the Rare logo brightens with game time and still differs a little),
  Mario Kart 64 (1.2%: the split of quads) and Majora's Mask's intro (0.23% at its 50th field from
  the state, 0.08% at the 100th, none by the 250th: F3DZEX's triangles fed back through S2DEX's
  framebuffer blur). Resident Evil 2's game scene: every non-triangle command the same (620,771),
  triangles close in 68% (F3DEX.Rej's slivers, both ways), pictures at most 0.067%.
- **Known differences.** F3DZEX point lights (Ocarina of Time). How F3DEX splits a quad in Mario Kart
  64: the diagonals (1, 2, 3) and (0, 1, 3) agree mostly, but no rule explains the choice; it shows
  only on warped quads. A shift of S by about 0.3 texel on some GoldenEye surfaces. Perfect Dark
  freezes the RDP between brief thaws: its microcode stalls on the full FIFO (about 23% of its time)
  while the HLE's task does not, so the SP interrupt comes earlier and long cutscenes drift by a field
  or so.

### S2DEX (`gfx_hle/s2dex.rs`)

S2DEX is the 2D microcode: object rectangles and sprites, and backgrounds copied or scaled to the
screen. Its builds 2.05 (Ocarina of Time's "[Safe]"), 2.06 (fifo and xbus) and 2.08 differ only in
where their code lies, the Safe build's pipe sync after each group of commands it hands over, and the
xbus builds' output, which the RDP reads from DMEM and of which it gets nothing the microcode had not
handed over when the task ends. S2DEX 1.x (GBI1; Resident Evil 2 has 1.06 in RDRAM, unused) stays
on the RSP.

The commands are the microcode's own steps, so that the RDP gets the same words. The arithmetic is
S2DEX's fixed point, run through the vector unit (`crate::vu`) one instruction at a time, because
its accumulator, reciprocal unit and lanes carry from one step to the next: a VADD leaves the
accumulator's high and middle slices from the last multiply, which a later VMADN saturates against,
and LDV fills four lanes and leaves the rest. Control flow is Rust. Its DMEM from 0x180 on is kept as
the microcode has it: its data, the object matrix at 0x1E0, the render mode and the tables it picks
at 0x1F8–0x268, the tile toggle at 0x2AE, the status words at 0x2B0, and its work from 0x3A8. Its
output gathers in a buffer as its own does and goes to the RDP where the microcode hands it over.
The vector registers carry from command to command, and what a task starts with makes no difference
to what is sent (checked with random registers).

What each command sends:

- **G_OBJ_RECTANGLE and _R** (the 2D matrix at 0x1E0): SET_TILE and SET_TILE_SIZE of the render
  tile (0 and 2 in turn, with a tile sync when it repeats), then TEXTURE_RECTANGLE.
- **G_OBJ_SPRITE:** the same tile setup, then two textured triangles through the 2D matrix.
- **G_OBJ_LOADTXTR (and the LDTX forms):** SET_TEXTURE_IMAGE, SET_TILE 7, then LOAD_BLOCK,
  LOAD_TILE or LOAD_TLUT, unless the status word at its sid already holds its flag under its mask.
- **G_BG_COPY:** strips of as many lines as TMEM holds, each loaded and drawn as a copy-mode
  TEXTURE_RECTANGLE; at the image's bottom, its last line and its top's first are loaded in two
  halves of TMEM.
- **G_BG_1CYC:** strips by the vertical scale, LOAD_TILE wrapping round the image's bottom, a
  TEXTURE_RECTANGLE each.
- **G_RDPHALF_2:** the scissor again, then the saved TEXTURE_RECTANGLE.

Quirks kept: G_BG_1CYC's test of an empty frame is CTC2, not CFC2, so it never ends early, and a
frame wholly outside the scissor makes about 65,000 strips, on the console too (the HLE stops after
8 million steps, which only a scale near 0 reaches); G_SETOTHERMODE_H/L do not mask w1.

**Checking.** `S2DEX_UCODES=DIR cargo test --release -p n64 --lib s2dex -- --ignored` runs S2DEX on
the RSP and the HLE on random lists, structures, render modes, cycle types, scissors, matrices,
status words and vector registers, and wants the same words. DIR holds `VERSION-text.bin` (8 KB of
text from its start in RDRAM) and `VERSION-data.bin` (2 KB), dumped from the games (not in the
repository); `S2DEX_TRACE`, `S2DEX_BUILD` and `S2DEX_SCALE` help. On all four builds every RDP word
was the same over 4000 lists each of rectangles, sprites and copies, 3985 scaled backgrounds, 3000
texture loads, 2994 mixed lists (calls, G_SELECT_DL, loads) and 2000 pass-through lists.
`--compare-hle`: every non-triangle command the same in Majora's Mask's intro (208,700 over 300
fields, 1,219,300 over 1600 from power-on) and Resident Evil 2's title (248,382), a cutscene
(114,600) and a game scene (620,771), on the Zero 2 W with the JIT too.

**Task time.** 30 cycles a command, plus, fitted to the microcode's RSP cycles on the oracle's lists
(within 3–8% for objects, 7% for scaled backgrounds, 21% for copies):

| Command | Base | Per RDP command sent |
|---|---:|---:|
| G_BG_1CYC | 270 | 15 |
| G_BG_COPY | 160 | 7 |
| Rectangles (with or without a texture load) | 80 | 44 |
| Sprites | 80 | 70 |
| G_OBJ_LOADTXTR | 40 | 34 |
| RDP commands passed on | 40 | |

### Audio HLE (`audio_hle.rs`)

With `--audio-hle` a sound task does not run on the RSP: its command list is read on the host CPU and
the work done on DMEM and RDRAM as the microcode does it. Nothing in it goes by game or by family of
microcodes. A task's microcode is known by its own code (`audio_hle/recognise.rs`), each command by
the routine its table entry leads to, looked up by its fingerprint in one library of routines
(`audio_hle/routines.rs`) that says what the routine does and how its code reads the command. The
commands' work lives in files by what it is: `adpcm.rs`, `resample.rs`, `envelope.rs`, `mixing.rs`,
`filters.rs` and `buffers.rs`. It knows today libultra's aspMain (ABI1: Super Mario 64, GoldenEye,
Mario Party 1–3, Rayman 2, Hexen, Episode I: Racer), Nintendo EAD's microcode in Mario Kart 64 and
another build of it in Ocarina of Time, and libultra's n_aspMain (Paper Mario, Donkey Kong 64). A
task with a command whose routine is not known runs on the RSP.

**Knowing a microcode by its code**

- **Where the code is.** The CPU loads the task's boot microcode into IMEM at 0x1000; that usually
  loads 0xF80 bytes of the microcode from 0x1080. A task whose boot microcode is the microcode itself
  (`ucode_boot` the same as `ucode`, as Ocarina of Time's) has it from 0x1000. The code is read from
  the task's text in RDRAM as IMEM has it (Ocarina of Time's was once read as if from 0x1080: its
  routines' fingerprints were of code 128 bytes off, which told them apart all the same).
- **The dispatcher** is the loop the routines go back to for the next command: where the code's
  jumps (J) go most. Its fingerprint (the loop and the code it reaches: the command's fetch, the list's
  and the task's end) picks one of the dispatchers this knows, and that says where the table of
  commands lies in the data (which the boot loads into DMEM at 0) and how many entries it has, the
  data its routines read (the first words, ADPCM's masks, the resampler's lane offsets, the lane
  selectors, the eighths, the filter's first taps: checked, so a microcode with the same loop and
  other data is not taken), and its own share of the RSP's time. Four are known: ABI1's (16
  commands at 0x10), Mario Kart 64's (24 at 0x10), n_aspMain's (16 at 0; two fingerprints, one for
  each build's loop) and Ocarina of Time's (24 at 0x10).
- **Each command** is the routine its table entry leads to, where the RSP's 12-bit PC lands in IMEM;
  an entry leading to the dispatcher does nothing. A routine's fingerprint is its instructions and
  those of the code it reaches by jumps, calls and branches (but the dispatcher), in the order
  reached, each without its jump target or branch offset: the same routine in another build, at
  another address or under another command has the same fingerprint, and constants in its code are
  part of it. Super Mario 64's and GoldenEye's builds have the same routines but ENVMIXER (its ramp),
  at different addresses; SEGMENT and SETLOOP are the same routines in ABI1 and in Mario Kart 64's
  microcode. A task with a command whose routine is not known runs on the RSP (`--compare-audio-hle`
  counts it as left to the RSP). The list is looked over before the task runs: most commands by their
  first byte alone (a bit for each command whose routine is known), the few whose routine runs here
  only with some words or with some commands before it by those too.
- **The library** has an entry for each variant of a routine, with the fingerprints of every code that
  does the same. An entry says what the command does and how its code reads w0 and w1: the packing
  (ABI1's commands work on SETBUFF's buffers; Mario Kart 64's and Ocarina of Time's carry their DMEM
  addresses and counts as libultra's later `abi.h` packs them; n_aspMain's as `n_abi.h` does, or work
  on n_audio's fixed buffers of 184 samples, with no SETBUFF or SEGMENT), the DMEM base its addresses
  are from (ABI1's 0x5C0, Mario Kart 64's 0x450, found by clearing buffers against the microcode,
  n_aspMain's 0x4F0, Ocarina of Time's none), whether it takes RDRAM addresses through SEGMENT's table
  or as they are (Ocarina of Time's command 7 is a filter, not SEGMENT), the constants its code has
  (where it keeps ADPCM's codebook in DMEM: 0x4C0, 0x3D0, 0x3F0, 0x330; where it reads the resampling
  filter in the data: 0xC0, 0x100, 0xB0, 0xE0; ENVMIXER's eighths: 0xB0, 0xA0), what it does where
  builds differ, and the RSP's cycles it takes. A constant changes the code, so a fingerprint stands
  for its constants. A new build of a known microcode needs only its new routines' fingerprints here
  (and the dispatcher's, with its time, if its loop differs).
- **What the code itself says.** The scratch a routine puts its state together in is what the start
  code sets s7 to (the first ADDI, ADDIU or ORI from zero into s7 before a jump, branch or break:
  0xF90 in ABI1); a routine that stages its state there is known only where the start code sets it.
  Where the task reads the filter and the eighths is the RESAMPLE's and ENVMIXER's its table leads
  to. A SETLOOP that keeps the loop's address in DMEM over the table of commands (n_aspMain's, at 0xE)
  makes the two entries it covers (7 and 8) lead elsewhere once it has run, so a task with them stays
  on the RSP.
- **Registers between commands.** Some routines take what the command before left in the RSP's
  registers, which the task's state keeps by what it is: Ocarina of Time's ENVMIXER its volumes (a
  block and the block after in a vector register) and their steps (in scalar registers, which it
  doubles) from ENVSETUP1 and ENVSETUP2, and its filter's run the count from the filter's setup; other
  routines overwrite those registers, so a task runs here only where they come right before (as
  Ocarina of Time's lists have them). Its ADDMIXER is left to the RSP: its VADD takes the carries of
  doubling whatever the routine before left in its register. The first VSUB of n_aspMain's and Ocarina
  of Time's RESAMPLE, and of Donkey Kong 64's ENVMIXER, subtracts the carries the RSP's last task (the
  graphics microcode, or the boot) left in VCO: those lanes of RESAMPLE's first block start half a
  step back. The HLE takes VCO from the RSP and gives back the VCO and VCC these microcodes leave; the
  comparison checks them too.

**The commands, by what they do**

- **ADPCM** (`adpcm.rs`): 9-byte frames (a scale and a book, then 16 four-bit residuals) decoded after
  the last 16 samples of the frame before (none, the loop's or the state's), which are kept; Ocarina
  of Time's also 5-byte frames of 2-bit residuals (flag 4) and takes its state's address at 8 bytes;
  n_aspMain's packs its flags, count, input and output in w1 and the state's address in w0. The
  prediction goes by lanes. The codebook lives in DMEM where the routine's code keeps it and LOADADPCM
  is a DMA there; a frame's book is 32 bytes on from it for each of up to 16 books, so books past
  those loaded are the buffers after it (Episode I: Racer decodes such frames, and the HLE once
  indexed past its table).
- **RESAMPLE** (`resample.rs`) works on eight outputs, reads a block's input before writing it (in
  GoldenEye the output overlaps four state samples before the input), always does at least one block,
  and keeps the last 4 samples and the phase; each of its four products is rounded on its own, as
  VMULF does. ABI1's and Mario Kart 64's also keep, for a loop (flag 2), the input's 16 bytes about
  where it goes on and their offset, put back before the input; ABI1's puts its 32 bytes together in
  the scratch and saves them from there, Mario Kart 64's straight to RDRAM (12 and 16 bytes).
  n_aspMain's keeps 10 bytes and picks its output among n_audio's buffers by w1's two low bits;
  Ocarina of Time's takes the pitch in w0, and its flags 2 and 4 (fewer or doubled samples before the
  input) are left to the RSP. DOWNSAMPLE_HALF keeps every other sample.
- **ENVMIXER** (`envelope.rs`) comes in three kinds.
  - *Ramping* (ABI1's, n_aspMain's), written out from the RSP code (the routine at `0x1B38` in Super
    Mario 64, read with a small disassembler). Left and right volume are vectors of eight lanes in
    16.16 (upper and lower halves). A note that starts (A_INIT) gives lane n the volume plus (n+1)/8
    of the step (the last one 0xFFFF/0x10000); each following block of eight samples takes the step
    once more: multiplied by the tempo in Super Mario 64's (VMUDL, VMADM, VMADN, VMADH), added in
    GoldenEye's and n_aspMain's (VADDC, VADD). The volume stops at its target: ABI1's compares
    unsigned rising (VCL without flags, for a rate above 0), n_aspMain's signed (VLT, for a rate of 0
    too), both VGE falling. Mixing is VMULF of the output by `0x7FFF` and VMACF of the input times
    volume times gain, with one rounding. The 80-byte state holds those vectors plus the targets,
    rates and gains that a continuing note takes from the state, not from SETVOL; ABI1's puts it
    together in the scratch (over the task's header at 0xFC0) and saves it from there. n_aspMain's
    mixes n_audio's fixed buffers of 184 samples into the main and auxiliary ones (always both), takes
    the right volume from its w0 when a note starts, and loads a continuing note's targets, rates and
    gains over SETVOL's own, so a later note without SETVOL goes on with them. Donkey Kong 64's turns
    a side's input over bit by bit where a gain is odd (the dry gain's low bit for the left, less
    VCO's carry, the wet gain's for the right); Paper Mario's does not.
  - *Stepping* (Mario Kart 64's): the input times the left and right volumes ENVSETUP2 keeps
    (unsigned fractions: `x·v >> 16`), negated bit by bit where asked (one below minus), into the dry
    left and right, and times the reverb's volume (ENVSETUP1's, 8 bits shifted up 8) too into the wet
    ones (swapped where asked), 8 samples at a time; the count rounds up to 8 samples, not 16. The left
    and right volumes step by ENVSETUP1's ramps after each block, the reverb's does not (the rest of
    that word is no ramp), and at 0 the wet buffers keep what they hold.
  - *From registers* (Ocarina of Time's): the left, right and reverb volumes as unsigned fractions,
    each moving on by its step every 8 samples (VADDC, wrapping), the dry sides negated bit by bit
    where asked and the wet ones with 0xFFFC and 0xFFFE (the microcode's own quirk), the wet sides
    swapped where asked, 16 samples a round with the outputs read before they are written in the
    microcode's order.
  - SETVOL sets ABI1's values one a command (the volume, or the target and rate, of a side, or the dry
    and wet gains); n_aspMain's three halves among the values the microcode keeps (the left volume
    with the dry and wet gains, the right target and rate, or the left target and rate). n_aspMain's
    command 14 (libultra's POLEF) has no routine: its entry, 0x02B0, lands in SETVOL's code, in Paper
    Mario's build on a store of w1's low half as the right rate's lower half (Paper Mario's lists use
    it), in Donkey Kong 64's elsewhere (a task with it stays on the RSP).
- **MIXER, INTERLEAVE and HILOGAIN** (`mixing.rs`). MIXER adds the input times the gain to the output
  with the one rounding of VMULF and VMACF (it used to round twice), in 32 bits:
  `out + ((x·g − out + 0x4000) >> 15)` equals the 48-bit accumulator shifted down 16 (tested on
  357 000 value triples). It goes in the order its code reads and writes, which matters where the output
  overlaps the input: as a sample at a time (ABI1's and Mario Kart 64's; 8 at a time where the output
  is not 2 to 14 bytes past the input), each block of 8 read before the one before is written
  (n_aspMain's), or 16 samples a round with the next round's input and output read between the writes
  (Ocarina of Time's). INTERLEAVE reads both sides before writing (Ocarina of Time's 4 samples of each
  at a time). HILOGAIN multiplies by a gain of 4.12.
- **POLEF and the 8-tap filter** (`filters.rs`). POLEF is a two-pole filter with the codebook's
  first two rows as coefficients; it scales the second row by the gain shifted up 2 in 16 bits and
  taken unsigned (VMUDM), so a gain of 0x4000 makes it 0, and writes it back; it reads its next 8
  input samples before writing the 8 outputs. Its two outputs before come from the scratch: the
  state's, or starting, with only the scratch's first 4 bytes cleared, what the command before left
  there. Ocarina of Time's filter has its setup (count, coefficients) as its own command; its run
  averages those coefficients with the state's (rounded up) and keeps the last 8 samples and the
  averages. Its 35-bit sum is two 32-bit sums by the samples' upper and lower bytes:
  `(high + ((low + 0x4000) >> 8)) >> 7` is exactly `(0x8000 + 2·sum) >> 16`.
- **Buffers** (`buffers.rs`): SETBUFF (ABI1's also the auxiliary buffers, flag 8), SEGMENT, SETLOOP,
  CLEARBUFF, DMEMMOVE (all read before any is written, or 16 bytes at a time), DMEMMOVE2 (its count,
  rounded to 32 bytes, that many times over, 32 bytes at a time, so a block repeats where the output
  follows it), LOADBUFF and SAVEBUFF: with SETBUFF's count, with their own in 16-byte units, or as
  n_aspMain's plain DMAs (both addresses at 8 bytes, the count rounded up to 8). Ocarina of Time's
  LOADADPCM, LOADBUFF and SAVEBUFF of nothing are left to the RSP (its DMA of 0 bytes moves 4 KB
  rows), and its HILOGAIN and DMEMMOVE2 off 16-byte boundaries.

**DMEM as the microcode leaves it.** The boot microcode loads a task's data (`ucode_data_size` bytes)
into DMEM at 0 before the microcode starts, and the HLE does the same. ABI1 assembles RESAMPLE's 32
bytes of state, ENVMIXER's 80 and POLEF's 8 in its scratch and saves them from there, so what one
command leaves there another may read: POLEF starting a sound clears only the scratch's first 4 bytes
and takes its two previous outputs from the next 4, and RESAMPLE saves bytes 12–15 as they were.
Mario Party and Mario Party 2 (POLEF) and Rayman 2 match the microcode on every task. Episode I: Racer
matches on all but a few: replayed command by command from the task's start, those match too; the
game changes a voice's state in RDRAM while the RSP runs the task, which the HLE, running it at once,
cannot see.

**Time.** The RSP looks busy for the dispatcher's cycles (a task, a command, fetching the list) and
each routine's (a fixed part, less where a note starts, and a part for each unit of its work), fitted
to the microcode's time: ABI1 52 a command plus a per-byte cost (420 tasks, under 1% off on average,
2% at most; the earlier estimate was 39% too long); Mario Kart 64's 64 a command plus a cost per unit
(2350 tasks, 0.1% low on average, 1.6% at most); n_aspMain 130 a task and 42 each 40 commands (1500
tasks of both builds, within 2% a task); Ocarina of Time's 109 a task and 52 each 8 commands (1200
tasks, within 0.3%). The picture can shift by one game frame as a result: the Super Mario 64 title
after 100 fields shows with the HLE what it shows without it after 98–99, and after 110 fields the two
agree again.

**Speed.** DMEM's samples are big-endian; the commands take them 8 at a time (one 16-byte access, each
pair's bytes swapped inside 32-bit words, which the compiler turns into NEON; it leaves 16-bit swaps
scalar) through a `Blocks` accessor: `Inside`, one branch-free access a block, where the command
checked that its buffers (and what it reads ahead) stay before DMEM's end, or `Wrapping`, byte by
byte, wrapping at DMEM's end as the RSP does. Tests run the commands with their buffers moved to
DMEM's end, across it and wrapped. Commands allocate nothing (states in fixed arrays, SAVEBUFF straight
from DMEM, copies in place in the microcode's order). On the Zero 2 W this took the machine thread
from 16.2 to 14.5 million cycles a field in Ocarina of Time (50.2 → 51.6 fps) and 2–3% down in Super
Mario 64's title, Mario Kart 64's race and Paper Mario. What the HLE gave the games there: Mario Kart
64's race 22.55 → 16.58 million cycles a field (41.2 → 53.5 fps in `run-n64`); Donkey Kong 64 17.10 →
13.85 million (54.4 → 65.1 fps) and Paper Mario 13.45 → 11.32 million (it stays at 39.5 fps, held by
its three drawing threads); Ocarina of Time 24.5 → 16.0 million (36.1 → 49.0 fps), 300 fields from
their states.

**Checking.** `--compare-audio-hle` runs the microcode as usual and the HLE on a copy of the machine
from the task's start, and compares everything the HLE wrote to RDRAM (and the VCO and VCC left,
where the next task takes them); on a difference it looks for the first command after which DMEM, or
RDRAM where the HLE wrote it, differs (the microcode on copies with a truncated list). It also lists
the audio microcode it does not know (where its data is, its size and its first 64 bytes) and counts
the tasks of known microcodes left to the RSP. Every command was settled this way against the
microcode, byte for byte, with the decompilations' `abi.h` and `n_abi.h` (Mario Kart 64's, Paper
Mario's) for the packing and a small RSP disassembler for the rest. Over 1600 fields from boot with
Start and A pressed, every task the HLE runs is the same as the microcode's: Super Mario 64 1563,
GoldenEye 774, Mario Kart 64 1558, Ocarina of Time 1018 (307 more left to the RSP), Paper Mario 1566,
Donkey Kong 64 757, Mario Party 1456, Mario Party 2 1434, Mario Party 3 1539, Rayman 2 3269, Hexen
1501, Episode I: Racer 457 of 464 (the race above); Majora's Mask's 1545 stay on the RSP (commands of
its build this does not know); Perfect Dark's, Resident Evil 2's and Battle for Naboo's microcodes are
not known. Earlier runs compared Mario Kart 64's intro, menus and races, 2000 tasks of Paper Mario
and of Donkey Kong 64 in play, and Ocarina of Time 1230 tasks from boot and 900 in play, also with the
graphics microcode on the RSP and on the Zero 2 W with the RSP's JIT.

The library and its recognition replaced a module for each microcode family (each with its own table
of commands, constants and costs) without changing a byte: against the code before, the comparison's
counts and notes over 1600 fields from boot (16 games with the graphics HLE, six of them also with
the graphics microcode on the RSP) and 600 fields from 17 states, and the sound, final state and
picture of 600 fields with `--audio-hle` (13 games from boot and 16 states with `--hle`, six games
from boot without it) are the same. On the Zero 2 W it costs nothing: the machine thread's cycles a
field (fastest mode, 300 fields from the states, four runs of each alternated with the code before;
medians) stay within the runs' spread: Ocarina of Time 14.36 million against 14.36, Paper Mario
10.78 against 10.82, Donkey Kong 64 13.63 against 13.63, Mario Kart 64's race 15.06 against 15.08,
Super Mario 64's title 17.39 against 17.37, GoldenEye 8.20 against 8.23. A first version, which
decoded every command of a list before the task ran, was 0.3–0.5% slower in Super Mario 64's title,
Donkey Kong 64 and Ocarina of Time; keeping each routine's loops out of line did not help.

### Video HLE (`video_hle.rs`)

Resident Evil 2 makes its logos and films on the RSP with three small microcodes, started as
graphics tasks with 0x80 bytes of data (parameters and vector constants): YUV 4:2:0 to 32-bit RGBA
into the frame buffer, the average of two 32-bit frame buffers, and a 24-bit picture 320 wide
scaled to RGBA5551 (bilinear, each group of eight pixels' error carried into the next). mupen64plus's
rsp-hle calls them decode_video_frame, fill_video_double_buffer and resize_bilinear.

- With `--hle` they run here, recognised by a fingerprint of their code and of the boot code at IMEM
  0. The boot code's work comes first (the data to DMEM 0, 0xF80 bytes of text to IMEM 0x80); then
  the microcode runs instruction for instruction: the same vector words go to the vector unit,
  vector loads, stores and DMA through the RSP's paths, and the scalar registers are kept. The YUV
  and blend loops go byte by byte with the vector unit's lane arithmetic while VCO was clear and the
  addresses are aligned, with the last group on the vector unit. DMEM, IMEM, RDRAM, the registers,
  the vector unit and the DMA registers come out as the microcode leaves them.
- The RSP looks busy for the microcode's cycles, from a cost model measured with the parameters
  varied that is exact under `rsp.rs`'s timing (YUV 322 + 112 a pass + 8 a row + 116 a group of 16
  pixels; blend 91 + 96 a pass + 13 a group of 8 bytes; resize 130 + 68 a row + 297 a group of 8
  pixels). Its last SP_STATUS write, the semaphore and the PC past the BREAK come when that time is
  up. A task that is yielded, has DP_WAIT or SIG0 set at its start stays on the RSP.
- `--compare-video-hle` checks every task in place (RDRAM written, DMEM, SP status when the RSP
  halts) and alone on two copies of the machine (all of RDRAM, SP memory, the registers, the vector
  unit, the DMA registers, status, cycles). Over the intro, 306 of 306 tasks are the same (145 YUV,
  143 blend, 18 resize), and the pictures every 150 fields to 1500 are those of the RSP.

- The RDP demos are checked by picture hash, after each was compared by eye with the collection's
  image. Those images are not from hardware (the fill colour differs from what is set, 16-bit colours
  are expanded differently, both fractals are one file, and the last three screen lines are outside
  what the VI shows), so the hashes are of this core's pictures. The 640 × 480 32-bit buffer matches
  pixel for pixel; the fractal differs by one palette step at band edges where the iteration count
  depends on the last bit; only IA4 greys differ, brighter here, though the decoding is angrylion's.
  The test takes each field's own picture (`set_rdp_exact_pictures`): the demos run thousands of
  fields a second, and the drawing thread's picture lagged by several to tens of fields.
  `--verify-rdp-thread` passes on all 84 krom RDP and RSP demos.
- **Super Mario 64 draws and plays** (`tests/boot.rs`): the logo at field 200 and the title screen at
  field 600, each a full picture in over 200 colours, and 10 seconds of clearly audible 48 kHz sound.
- **Game boot** (`tests/boot.rs`): Super Mario 64, Mario Kart 64, GoldenEye (CIC 6102), Paper Mario
  (6103), Ocarina of Time and Donkey Kong 64 (6105). The game's IPL3 reaches the entry point, the
  first megabyte of the game lies in RDRAM at the entry address, `0x318` holds the RDRAM size (8 MB),
  and for DK64 the RSP's IPL3 copy exists. The games are not in the repository: the tests read the
  ROMs from `N64_ROMS` (default `/tmp/n64-roms`) and skip with a message without them.
- **Saves** (`tests/saves.rs`): each of the six games gets save memory of its size. On empty EEPROM
  Super Mario 64 writes four files and the menu data at start (two copies each, with signature and
  checksum); in the next session, with file A holding stars and a corrupt backup, it rewrites the
  backup from the good copy. EEPROM goes through a save state.
- **Save states** (`tests/state.rs`): after a load, the fractal, the timer-interrupt test and Super
  Mario 64 (if present) continue field for field as before (picture and CPU registers); a state of
  another game, a truncated one or an empty one is rejected.
- **Unit tests:** ROM byte orders, reads past the end of the ROM, decoder fields, FPU rounding modes,
  EEPROM, SRAM (also banks), FlashRAM step by step as libultra drives it, the game list, the CIC 6105
  answer, and the DK64 triangle whose spans lie left of the screen.
- **Fast paths against the reference.** The idle-loop tests compare the optimised path with executing
  every instruction (14 kinds of jump, even and odd event boundaries, interrupts with EPC/BD, a code
  change after an event, fetch exceptions, slots with side effects). Every other fast path has
  randomised tests that compare the whole state with the reference (the CPU dynarec on ARM, 3000
  random RSP programs, each NEON vector function on all element fields and alias layouts, the RDP
  spans, combiner and blender) and a `--verify-*` flag (see Tools) that does so after every field of
  real games. Six games after 600 fields and Super Mario 64's first 40 fields match byte for byte on
  the whole state, PPM and WAV; Majora's Mask, Perfect Dark and Episode I: Racer match on picture,
  sound, cartridge memory and CPU registers.

krom's tests draw PASS in green or FAIL in red; the test looks for those words glyph by glyph (using
the collection's font files) anywhere in the frame buffer. The full suite, with the downloaded ROMs and
the games, passes on the PC and on the Zero 2 W (where the ROM suites skip); single-instruction
microbenchmarks are skipped.

Not passing, on purpose for now (`cargo test --release -p n64 -- --ignored` runs them):

- krom's timing tests (CPUTIMINGNTSC and CP1TIMINGNTSC, 22 cases each): they need real instruction
  cycle counts, and the interpreter counts every instruction as one;
- short PI DMAs to unaligned RDRAM (DMAAlignment-PI-ROM-FROM, 5 of 22 cases): the DMA copies
  everything at once, without the first-block oddities described on n64brew;
- unaligned SP DMA (3 of 22 and 3 of 23 cases);
- undocumented vector opcodes (the tests' VACC and VSAC are 0x1E and 0x1F, which accumulate
  something, and the VEXT group; no microcode uses them).

Resident Evil 2 used to stop at about field 250, after the N64 logo, with and without the HLE,
while the reference emulator (parallel-n64, angrylion and cxd4) went on. Every thread waited in
`osRecvMesg`. Its scheduler keeps a state byte for each kind of task (0x80112969 for the frame's):
an SP interrupt sets the running one's to 7 ("RSP done"), the DP interrupt then moves it on, and the
main loop is woken only in state 3. Our DP interrupt came before the SP one, so the SP interrupt of a
finished task left the state at 7 for good (see "The DP interrupt" above); now the game plays its
intro as the reference does, at the same fields. The way there, without symbols: the threads found by
their libultra layout in an RDRAM dump (state at 0x10, saved PC at 0x11C, SP at 0xF4), the event
table (`osSetEventMesg`'s) by the VI manager's queue, the scheduler's message ring, and guest PC
probes and a byte watch in the interpreter (in a copy of the source). Its idle thread counts in its
loop (`b .` with `daddiu a0, a0, 1` in the slot), 73% of its film's instructions. Idle-loop skipping
now also takes a delay slot that counts (ADDIU or DADDIU of a register the branch does not read),
adding the count at once; the machine after 1500 fields is byte for byte the same. On the Zero 2 W

## Tools

- `cargo test --release -p n64` (in `emu/`) builds and tests the core. Fetch the public test ROMs first
  with `emu/n64/tests/roms/fetch.sh`; the games are read from `N64_ROMS`.
- `cargo run --release -p n64 --example run-n64 -- ROM FIELDS out.ppm [EVERY] [options]` runs a ROM
  headless, saves the picture (PPM) and sound, and prints the IS-Viewer text and the CPU registers.

Options of `run-n64`:

| Option | Effect |
|---|---|
| `--wav FILE` | save the sound of all fields |
| `--save FILE` | load the cartridge's save memory from FILE (if it exists) and write it back at the end |
| `--press BUTTON@FIELD` | hold a button for 6 fields from that field (a, b, z, start, up, down, left, right, l, r, c-up, c-down, c-left, c-right) |
| `--warmup N` | emulate the first N fields but leave them out of the timing |
| `--state-in FILE`, `--state-out FILE` | resume from a saved machine; write the final one (for repeatable scene benchmarks and byte-for-byte comparisons) |
| `--jit`, `--interpreter` | CPU dynarec on, or the reference interpreter (ARM only) |
| `--jit-stats` | collect counters (block counts, the RSP's two counters, the RDP's three); their hot path is off otherwise |
| `--verify-jit` | run both machines and compare picture, sound and the whole save state after every field; needs an ARM build and at least one natively executed instruction, so it cannot pass vacuously on a PC |
| `--rsp-scalar` | turn off NEON and the fast RSP memory transfers |
| `--rsp-memory-reference` | turn off only the transfers (to measure their cost) |
| `--rsp-vector-reference` | turn off only NEON |
| `--rsp-interpreter` | turn off the RSP dynarec |
| `--verify-rsp` | compare the accelerated RSP with the scalar one and the byte loops after every field; requires that a fast path actually ran; the memory transfers also work off ARM |
| `--rdp-reference` | the previous rasteriser (no RDP accelerations) |
| `--rdp-rgba16-reference`, `--rdp-memory-reference`, `--rdp-combiner-reference`, `--rdp-span-reference` | turn off one acceleration: the RGBA16 decoder (the three-texel filter stays), skipping image reads, the plan-based combiner, the 1-cycle span loop |
| `--verify-rdp` | compare picture, sound and whole state after every field with all CPU, RSP and RDP accelerations off; requires that the faster filter, the RGBA16 decoder or skipped reads were used |
| `--rdp-threads N`, `--no-rdp-thread` | number of drawing threads (default: all cores but the machine's, at most 3); draw on the machine thread |
| `--verify-rdp-thread` | compare, after every field, with drawing on the machine thread (also checks drawing running ahead by many fields) |
| `--check-rdp-marks` | draw on the machine thread and check after each draw that only the pages it marks changed |
| `--exact-pictures` | take each field's own picture |
| `--hle`, `--compare-hle` | graphics HLE; compare its RDP commands with the microcode's for every graphics task |

### Starting point

- On a PC (i7-12700K) the interpreter runs about 185 million VR4300 instructions a second. Super
  Mario 64 with the RSP and RDP runs at 66–86 fps (intro, title screen, castle); before they existed
  it was 178; krom's fractal 158.
- The interpreter always executes 1.56 million guest instructions a field (93.75 MHz / 60), idle
  loops included, at about 135 ARM instructions each (fetch with address translation, decode,
  execute, event and interrupt checks), and about 300 for an FPU instruction. At about one
  instruction a cycle on the Cortex-A53 that is 212 ms a field for the CPU alone: 13 times too slow
  for 16.7 ms (28 times on FPU-heavy code). With the RSP and RDP, Super Mario 64 costs 307 million ARM
  instructions a field: the interpreter CPU 76%, the RSP 15% (its vector unit 12 million), the RDP 9%.
- A cheaper interpreter (decoded instructions cached by page, idle-loop skipping, a fast FPU path)
  might give 2–4 times, not enough. Full speed needs what mupen64plus has: a CPU dynarec (a few ARM
  instructions per MIPS instruction, no decode at run time), HLE or a dynarec for the RSP, and a
  fast RDP. The interpreter stays the reference.

### Optimisations by subsystem

The largest gains, with the measured change in machine-thread cycles a field (Pi) or ARM
instructions a field (QEMU) on the scenes above, or in fps. "Before the castle" is the SM64 gameplay
scene.

**CPU interpreter**

- Idle-loop skipping: SM64 title 452.34 → 293.46 million ARM instructions a field (−35.1%), the
  fractal 547.92 → 509.71 (−7.0%), pictures identical.

**CPU dynarec**

- The first stage (integer arithmetic, RDRAM loads and stores, jumps) did not pay yet: title 300.20
  → 292.58 million ARM instructions, the fractal 544.88 → 619.08. Blocks averaged 2.5 instructions.
- Interpreter calls inside blocks (blocks grew to about 6 instructions): title 189.6 → 172.0 million
  cycles (−9.3%), before the castle 152.6 → 144.7 (−5.2%). Native FPU loads, stores and moves, about
  15% of the title's instructions: a further −9.4% and −4.2%.
- Running beside the RDP thread (page marks in native accesses): title 5.3 → 8.7 fps, before the
  castle 6.1 → 13.1 fps.
- Mapped code with the TLB page memory: GoldenEye at the barrel 1.9 → 78 fps (machine thread 510 →
  11.6 million cycles). Its code runs at `0x7000_07xx`, which the dynarec used to skip, and
  `tlb_lookup` was 18% of the thread.
- Native FPU arithmetic, compares and conversions: single precision title 105.0 → 93.5 million
  cycles; C.cond.S and CVT.S.W Ocarina of Time −6.2%; interpreter calls from blocks over 12 fields
  12.7 → 2.3 thousand (before the castle), 25 → 7.9 (title), 17.9 → 2.9 (DK64).
- Delay slots: the plain-arithmetic slot in the block (title 93.5 → 87.4); loads and stores and FPU
  instructions in slots (interpreter-run slots over 130 fields: GoldenEye 483 → 33 thousand, before
  the castle 698 → 67 thousand, title 817 → 212 thousand); one control-state write a branch (before
  the castle −4.3%, title −3.3%).
- Linking: blocks back to back in a page (GoldenEye 70.3 → 73.2 fps); links in ARM code (title 32.1
  → 34.7 fps, before the castle 45.0 → 48.7, GoldenEye 72.7 → 79.7); links for calls, returns and
  other pages raised the share of blocks entered through a link (before the castle 67% → 88%, title
  60% → 81%, Mario Kart 64 77% → 90%) for another −4.6% and −6% cycles; a lighter link routine −2.9%.
- Code size: shared guard routines (13 → 3 instructions an access, before the castle 56 → 59.3 fps)
  and shared FPU arithmetic routines (FPU had been 31% of all code; before the castle 57.5 → 60.1
  fps). The code memory grew from 16 to 32 MB because Ocarina of Time overflowed it (about 17
  thousand blocks in one scene, recompiled twice in 70 fields).
- Code changes: comparing a block's source only after a write into code (it had been 8.7% of the
  thread; title 45.7 → 43.2 million cycles); code tracked in 256-byte chunks, because Ocarina of Time
  changed generation about 1060 times a field when actor variables shared pages with code (30.3 →
  25.7 million cycles, −15%, 29.0 → 33.7 fps).
- Registers held in r6–r10, guards of four words with one LDRD, direct branches to the routines and
  cheaper compiling (2026-11-03, 300 fields from the states, machine thread a field): Super Mario 64
  title 19.17 → 17.28 million cycles (47.9 → 52.9 fps), Mario Kart 64's race 16.86 → 15.74 (53.8 →
  57.1), Ocarina of Time 16.23 → 15.07, GoldenEye 9.05 → 8.60 (97.5 → 101.7). Direct branches alone
  took the title from 18.8 to 17.6 million and compiling without allocations the race from 16.70 to
  15.74. Exits and compiled blocks counted by `--jit-stats` are the same as before.
- Native MFC0/MTC0 of Status, block ends that write the control state once (after the slot, with
  STM/STRD/STRH; the slot's exits write the branch's state in a routine of the block), links checked
  without a search (a set for each way of a branch, the PC in registers, a word of cycles left)
  (2026-11-03, Zero 2 W at 1300 MHz, 160 fields after 40, machine thread a field, base and new
  alternated): Star Wars Episode I: Racer 61.9 → 50.0 million cycles (−19%, 19.5 → 23.8 fps), Super

  from the drawn rows only: before the castle 36.6 → 40.0 fps, title 18.6 → 23.2. Waiting for the
  draw itself (sequence numbers): Ocarina of Time had read a word of game data next to the depth
  buffer once a game frame and waited about 44 ms for the depth clear and everything batched after
  it; 20.4 → 29.0 fps (+42%).
- Opaque span without alpha (RDP-thread cycles): title 28.0 → 21.2 million (−24%), before the castle
  56.1 → 49.0 (−13%); widened to IA8/IA16 and force_blend returning the combiner colour, 19.1 and 39.5;
  untextured spans and plain alpha blending, Mario Kart 64 54.9 → 33.6. Texel × primitive combiner
  (99% of DK64's pixels): 25.1 → 27.6 fps. General combiner without per-pixel mode decoding:
  Ocarina of Time −11.5%. Any one- or two-cycle span with its modes worked out once
  (`span_cycles`) and copy-mode spans (`span_copy`), on the Zero 2 W (300 fields from the states,
  drawing-thread cycles a field): Paper Mario 18.3 → 13.2 million (39.3 → 49.2 fps), Ocarina of Time
  23.2 → 18.0 million (38.2 → 39.7 fps, then held by the machine thread at 22.5 million); with
  samplers fixed per tile and the pass-through blender cycle, Ocarina of Time 18.3 → 16.9 million
  (48.4 → 50.9 fps, after its audio HLE).
- More threads: before the castle 21.9 → 32.5 fps with two, 33.5 with three; Paper Mario 51 → 59–66
  fps and Mario Kart 64 69 → 82 going from two to three. The barrel scene loses (75 → 69 fps: three
  threads meet at every VI picture).
- Fewer copies in the machine thread (TMEM word loads, only changed TMEM bytes sent, no allocation per
  HLE triangle, clipping in fixed arrays): before the castle 25.8 → 23.6 million cycles, GoldenEye
  22.7 → 20.0.
- NEON spans, fill rows, compressed depth test, triangle setup (2026-11-03, Zero 2 W, 300 fields from
  the states, drawing-thread cycles a field, base and new alternated): before the castle 16.8 → 13.2
  million (−21%, 57.8 → 68.4 fps), Ocarina of Time 16.9 → 11.9 (−30%; 50 → 52 fps, held by the machine
  thread), Paper Mario 13.4 → 8.75 (−35%, 62 → 74 fps), Mario Kart 64 12.0 → 8.3 (−30%), Donkey Kong

  the waits for loads and the NEON chains' latencies, which the in-order A53 does not overlap, are
  much of what is left. The ARM binary grew from 5.8 to 7.4 MB (64 NEON opaque loops beside the scalar
  ones) without more L1I refills.

**Graphics and audio HLE**

- F3D without the RSP: machine thread title 143 → 111 million cycles, before the castle 80 → 50 (the
  RSP's 520 thousand cycles a field → 19 thousand); with `--jit` 11.3 → 14.7 and 17.2 → 22.6 fps.
- F3DEX2: DK64 27.5 → 45.2 fps, Paper Mario 45 → 49. Ocarina of Time first lost (12.4 → 11.6 fps

- F3DEX 1.x and default lights: Mario Kart 64 after 600 fields 16.4 → 68.5 fps.
- Audio HLE: before the castle 38.7 → 42.8 fps, title 23.7 → 30.3, GoldenEye 52.0 → 64.6, barrel

### Tried and dropped

- **RSP audio tasks on their own thread** (commit `f20613c`, `--rsp-thread`): a copy of the machine
  ran only the RSP while the main thread ran the CPU. No gain: the machine waited at every slice,
  because an RSP cycle costs the host far more than a CPU cycle.
- **Skipping the block source compare with a generation counter, first attempt:** 2–3% slower
  (before the castle 23.8 → 24.4 million cycles). Only 19% of compares were skipped (36% in GoldenEye)
  because reads of code pages bumped the counter. The second version, bumping on writes only, helped.
  A benchmark pitfall from it: `git archive` stamps files with the commit date, so a build in an old
  `target` directory can silently skip a rebuild; `touch` the files first.
- **Shared full load/store routines** (the block passes only instruction fields): fewer L1I fills but
  more cycles, title +5%, GoldenEye +3%, before the castle +1%. Shared routines pay where the shared
  part is large and the arguments few (guards, FPU arithmetic).
- **A separate short exit for each guard:** +0.3–1.6% cycles.
- **FPU fast path that required all enables clear:** slower (title 105 → 120 million cycles), since
  libultra sets FCR31 = FS | EV and every operation left the block. Exits must be rare.
- **Inline memory guards** (about 14 words each, 84 bytes a guest instruction): only 2% fewer cycles
  than shared ones, as the hot code is far beyond the L1I and L2. Calling the link routine with a
  `ldreq pc` in each block was slightly slower, and a rescheduled link routine gave nothing.
- **A 512-entry table of recent blocks** in front of the lookup: +2–3% cycles.
- **Link check in every block** (about 30 instructions a link): DK64 +2.4%, Ocarina of Time +4.6%.
- **`mem::swap` of the clip polygon arrays** (6.7 KB copied a triangle): slower title and DK64.
- **Smaller drawing-thread batch entries, or batches that start at 128 entries and 4 KB TMEM:** no gain,
  or +0.8% cycles.
- **Three drawing threads at the barrel scene** (little drawing, a barrier at every VI picture): 75 →
  69 fps. They stay the default.
- **A texel's three loads written phase by phase** (without the asm block between): the compiler put
  them back one texel after another.
- **Reading the image's pixel before the combiner's result in span_cycles:** Ocarina of Time +0.6%
  cycles (pixels that the alpha tests then drop read it too).
- **Storing a pixel's colour while the next pixel's texels are filtered** (one asm block for both
  chains, the store deferred past the next depth test, only where colour and depth images do not
  overlap): before the castle −0.8%, Donkey Kong 64 ±0; not worth reordering stores.
- **Side branches in the CPU dynarec** (2026-11-03, Zero 2 W at 1300 MHz, machine thread a field
  against the same build without them): a block went on past a conditional branch with a plain slot
  where it was not taken, out through a link of its own where taken, and a block out of words linked
  to the next. Star Wars Episode I: Racer 50.3 → 47.7 million cycles (−5%), but Mario Kart 64 +1.4%,
  Majora's Mask +2.1%, Paper Mario +2.4% (Ocarina of Time +1.2% at 1000 MHz): Mario Kart 64 entered
  17% fewer blocks, but compiling the longer blocks cost more than the links saved (its compiler is
  about 6% of its machine thread). At most two a block still cost those three about 1%; with likely
  branches and load, store and FPU slots too, every game was slower (Mario Kart 64 +38%).
- **Product cycles as separate combiner kernels chosen per pixel:** the larger loop spilled more
  (Ocarina of Time +1.6% cycles); a branch inside the one kernel instead.

## On the console

The game host (`solhost`, not published yet) runs the N64 core in its fastest mode: the CPU
dynarec, RSP and RDP accelerations, graphics and audio HLE, and the RDP on its own threads.

- The picture changes size with the game (320 × 240, 640 × 480 interlaced) and is shown at 4:3. While
  a game has the video off, the last picture stays.
- The pad's left stick is the N64 stick (the pad's travel is scaled to 80 of 127, as far as a real
  stick goes). The right stick, and Xbox B, Y, View and the right trigger, are the C buttons; A and X
  are the N64's A and B, and the shoulder buttons are Z and R.
- The 32-bit Zero 2 W and 64-bit handheld builds have all the CPU and RSP dynarec fast paths.

## Next

- **CPU dynarec.** Code size matters (L1I and L2) but not at any price. In Star Wars Episode I:
  Racer's race the link routines are about 11% of the machine thread, the guard routines 14% and the
  FPU's 10%. Compiling still matters in Mario Kart 64: about 6% of its machine thread, and it still
  compiles about 42 new blocks a field after 60 fields with no code changed (new entry points, as
  after exits in the middle of blocks?); finding why comes before longer blocks (see Tried and
  dropped). MFC0 of Count, 32-bit ARM DMULTU/DDIVU routines, and rarer FPU work
  (L conversions on A32) still go through the interpreter.
- **RDP on the Pi.** With NEON spans the drawing threads run at about one instruction a cycle; the
  waits for loads and the NEON chains' latencies, which the in-order A53 does not overlap, are much of
  what is left. In the machine thread: page checks and sends to the RDP threads and the VI picture
  (about 5% together).
- **Beyond that,** the RDP on the GPU (KMS/GLES) needs its own measurements against the reference.
- **Audio HLE** for more routines as other games show them (the Zelda build's ADDMIXER, DUPLICATE,
  RESAMPLE_ZOH and 8-bit decoding; Mario Kart 64's POLEF): `--compare-audio-hle` counts the tasks
  left to the RSP for routines this does not know.
- **Graphics HLE.** F3DZEX point lights; Ocarina of Time's RDP commands spread over the task as the
  microcode does (the CPU now waits for the whole frame); the rule by which F3DEX splits a quad
  (Mario Kart 64); the 0.3-texel S shift on some GoldenEye surfaces.
- **RDP accuracy.** Coverage and antialiasing, dithering, LOD and mipmaps, YUV, chroma key; the time
  of RDP and RSP work (RDP commands now run right after the DPC_END write).
- **RSP pipeline.** Vector register delays and pair conflicts.
- **Pads and cartridge.** Controller Pak (saved on the pad's card), Transfer Pak; the RTC
  (Animal Forest) on the cartridge channel; 1 Mbit SRAM (Dezaemon 3D, from the homebrew header);
  EEPROM write time and FlashRAM erase time (both instant now).
- **Picture.** GoldenEye's holes in the chrome Nintendo logo and its noisy menu icons.
- **CIC 6106 games** (F-Zero X, Yoshi's Story) need a check on a real game: the entry point is from the
  table, and none has been tried yet.
